# paper-review-deepseek — 把论文发给 DeepSeek，然后**你**判断并修改

> 这份说明是写给**工作 AI**（正在处理这篇稿子的那个 agent）的。下面所有"你"都指工作 AI。
> 交给你之前，工具部分已经跑通、验过；论文本身**没有被任何人动过**——改稿是你的活。

一个循环，四步：

1. **发** — 把 `.tex` 以真实附件发给 DeepSeek（不粘贴正文），问一个写死的问题。
2. **判** — 逐条判断：哪些成立、哪些是它读错了、哪些需要补证据。**这一步不能外包回去。**
3. **改** — 只对站得住的那部分意见动论文。每条改动留出处。
4. **再发** — 改完再问一次，但**不要看分数**，看上一轮的问题还在不在。

DeepSeek 只提供"一个没见过你实验记录的外部视角"，不提供裁决权。
把它的意见原样执行，等于让一个读者指挥改稿。

---

## 最重要的一条：分数是噪声，观点才是信号

同一个稿子、同一个附件、同一个提问，问两次：

| 轮次 | 总分 | 出处 |
| --- | --- | --- |
| 8 维度加权评分卡 | **5.46** | 早期 `src/rubric.mjs` |
| 默认镜头「请评价、打多少分」 | **7.5** | 单次 |
| `score-dims` 第 1 次 | **8.5** | `--lens score-dims` |
| `score-dims` 第 2 次（同附件） | **8.2** | 重复实验 |

同一份稿件在四组实验里拿到 **5.46 / 7.5 / 8.2 / 8.5**，分维度漂移 0.5–1.0。

**所以：不要用分数做判据，不要追求"把分数问准"。** 分数只说明它此刻的情绪。
反过来，两次互相独立的 `reject-tie` 指出的缺陷高度重合——**重合的部分才是可核验的信号**。

由此得到本包的核心用法：**用镜头找问题，不用镜头定分。**

## 第一步：发

```bash
# 默认：只要一个分数
node tools/ask-paper.mjs paper.tex

# 换一个观察角度（一次可以问多个，附件只上传一次）
node tools/ask-paper.mjs paper.tex --lens reject-tie,selfdeceive

# 全部镜头
node tools/ask-paper.mjs paper.tex --lens all
```

### 提问是写死的常量，不可从命令行传入

`tools/ask-paper.mjs` 里的 `PROMPT`，23 个字：

> 这是我的论文，请评价一下，满分10分打多少分？

**没有 `--question` 之类的开关，这是故意的。** 上限 50 字（`PROMPT_MAX`），超了模块直接抛错拒绝加载。
理由两条：换问法等于换尺子，纵向就没法比；以及防止有人把长 prompt 塞进来，那就变成"让人代写指令"而不是"让模型自己思考"。

要给 DeepSeek 追加要求，**改源码常量**，别在命令行里塞。

### 镜头菜单（17 条，全部 ≤50 字，全部写死）

每条镜头两句固定后缀会自动拼上（`PINS`，19 字）：
`请用中文回答。` + `每条后标注章节或公式号。`
前者防止两次回复一中一英导致无法比对；后者让"同一处抱怨"能被识别成同一件事，而不是同一措辞。

| 镜头 | 问的是 | 什么时候用 |
| --- | --- | --- |
| `score`（默认） | 请评价，满分 10 分打多少分 | 第一轮，要一个整体印象 |
| `score-dims` | 打分，各个方面打多少分 | 想要分项表而不是一个总分 |
| `reject` | 最可能被拒稿的理由是什么 | 快速找致命伤 |
| `reject-tie` | 假如你是 IEEE TIE 的审稿人，你将如何拒稿 | **信号最强的一条**，会给成稿级审稿意见 |
| `reject-tpel` / `reject-tim` / `reject-tcst` | 同上，换期刊 | 换刊重投前 |
| `probe` | 你作为审稿人最想追问哪一点 | 找它最不确定的地方 |
| `boundary` | 适用边界在哪，超出怎样失效 | 判断适用范围写没写清楚 |
| `simpler` | 有没有更简单的替代解释 | 防过度理论化 |
| `selfdeceive` | 作者在哪里说服了自己但没说服读者 | **信号很强的第二条** |
| `transfer` | 换一个领域还成立吗 | 检查结论普适性 |
| `novelty` | 真正新的东西只有哪一点 | 检查贡献陈述 |
| `hides` | 最不该被默认成立的假设是哪个 | 找隐含前提 |
| `reader` | 不了解这个课题的读者会误解哪一点 | 检查可读性 |
| `next` | 只有一个月最该补哪一件事 | 排优先级 |
| `top` | 和该期刊顶尖高引论文的区别是什么 | 判断野心是否匹配 |
| `sweep` | 逐节检查，每节至少指出一个问题 | **单次覆盖最高**，见下方实测 |

**先挑哪条镜头？** 如果只问一次，用 `sweep` 或 `reject-tie`——这两条在"能不能找出真实缺陷"上有实测数据（见下）。

**关于镜头数量的实测结论**（别在这里纠结）：

用 4 条镜头 × 2 次重复跑同一篇稿子，测"换镜头比重复运行更不一样吗"：

| 测度 | 同镜头重复 | 换镜头 | 比值 |
| --- | --- | --- | --- |
| 句级词面重合 | 17.0% | 2.1% | 0.13 |
| 独立定位符重合 | 40.2% | 15.0% | 0.37 |

两个测度同向：**换一个镜头，重合度低于再问一遍同一个镜头**。所以菜单不是在重采样，加镜头有真实增量。

但另一件事没测出来：**各镜头的边际产出无法可靠排序**。试过按"该镜头有多少条是别的镜头没提的"排名，结果是几乎每条都 100% 新增——这个检验检测不到冗余，不能用来删镜头。

**所以：按判断裁剪菜单，不要按这份数据裁剪。** 如果嫌慢，先删期刊变体（四选一），再删 `transfer` / `novelty`（信息通常已被 `reject-tie` 覆盖）。

### 哪种问法真的能找出缺陷（有 ground truth 的实测）

上面那些测度测的都是"两次回复像不像"，不是"找得对不对"。为了回答后者，拿一篇稿子（`TAC\论文19`，18 KB，max-plus 矩阵周期性与灵敏度）自己通读全文，列出 **6 条逐条可核对的真实缺陷**，再拿它给每种问法判分：

| 配置 | 调用次数 | 覆盖 | 单次平均 |
| --- | --- | --- | --- |
| 4 条镜头（`reject-tie`/`hides`/`probe`/`reader`）× 2 次 | 8 | 6/6 | 3.00 |
| 枚举式三问（`sweep` 等） | 3 | 5/6 | 3.67 |
| `sweep` + `reject-tie` | **2** | **6/6** | **5.00** |

复跑一次 `sweep` + `reject-tie` 仍是 6/6（单次平均 4.50），**结论可重复**。

三点推论：

1. **整体式提问会"采样"**——`reject` 这类问法提 3–4 条就停，所以要多问几次才凑齐。`sweep` 把"采样"换成"枚举"，单次覆盖从 3.0 升到 5.0。
2. **便宜配置不总是够**。换另一篇稿子（`TAC\论文01`，39 KB，双 EKF），两套配置的发现只重合 36%，说明它们看的不是同一批问题。所以 `sweep` + `reject-tie` 是**默认起点**，不是唯一答案。
3. 别把这张表当成"8 次不如 2 次"的证明。它只说明：**在已经有 ground truth 的那篇稿子上**，枚举式两问没有漏掉任何一条。换稿子要重新验证。

### 追问：让它自己交代哪些没核实

第一轮回答里的每一条，读起来都一样有把握——但它自己知道哪些是查过原文、哪些是凭经验补的。追问一句就能把这两类分开。

`--follow` 会在**同一个会话里**发第二轮（靠 `sessionId` + `parentMessageId` 续上，所以"上面"仍然指上一条回答；开新会话问这句话毫无意义）：

| 追问 | 问的是 | 什么时候用 |
| --- | --- | --- |
| `verify` | 上面哪几条没在原文中核实过 | **默认加这一条**，决定先查什么 |
| `evidence` | 最关键那条的原文行号和原句 | 动笔改之前确认真在那 |
| `strongest` | 只能保留一条，保留哪条 | 意见太多、时间不够 |
| `counter` | 上面哪条可能是我误读了原文 | 怀疑自己被带偏 |

```bash
node tools/ask-paper.mjs paper.tex --lens sweep --follow verify
```

实测（`论文19`，`sweep` → `verify`）：它把自己上一轮的 11 条逐条分开，明确指出「定理陈述、公式、枚举规模、声明文字我核对过；但所有"novelty 不足、不严谨"的定性评价都是我的外部判断」。这一段比第一轮的全部内容更有用，因为**它告诉你不该先花时间在哪**。


### 一个镜头可以跑多次，但只有跨镜头一致才算数

同一条镜头问两遍，回答会高度相似——这**只能证明自洽，不能证明正确**。同一个问法带着同一个偏误，重复一百次还是同一个偏误。

**接受一条意见的门槛是：至少两个问法完全不同的镜头，各自独立地撞到了同一件事。**

`tools/round-report.mjs` 就是干这个的。喂它同一篇稿子的多个 JSON（镜头可以任意组合、每个镜头可以跑多次），它按论文聚合，把每条意见归到"几个镜头都提到"：

```bash
node tools/round-report.mjs \
  feedback/reject-tie-r1.json feedback/reject-tie-r2.json \
  feedback/hides-r1.json      feedback/hides-r2.json \
  feedback/probe-r1.json      feedback/probe-r2.json \
  -o feedback/round-1.md
```

输出分三栏，**只有第一栏可以用来改稿**：

| 栏位 | 含义 | 怎么用 |
| --- | --- | --- |
| **多个镜头都提到**（≥2 个镜头） | 不同问法各自撞到同一个问题 | 唯一可据以改稿的一栏 |
| 只有一个镜头反复提到 | 该问法内部一致，无人佐证 | 可能是这个问法自带的执念 |
| 只出现过一次 | 一次性 | 需要你自己核实 |

`--min-lenses` 调门槛（默认 2），`--min-runs` 调合计出现次数（默认 2）。

**实测（论文19，4 镜头 × 2 次）：跨镜头一致 5 条，其中 2 条被三个镜头同时指到。** 这 5 条和"单镜头重复"那栏的 6 条，质量差距一眼可辨——后者全部是 `reader` 在反复说"读者会误以为……"，因为那个问法本来就在问误解。

### 产出

默认写到 `./.deepseek-feedback/`（`--out` 可改，**不写到论文旁边**）：

- `<paper>.feedback.md` — 回复原文，**不加工**
- `<paper>.feedback.json` — 同上，机器可读，便于跨轮比对
- 多镜头时默认 `<paper>.lenses.md`

## 第二步：判（你来）

### 准入门槛：多个镜头都提到的，才进入判断

不要拿到一条回复就逐条判断。先跑 `round-report.mjs`，只对**「多个镜头都提到」那一栏**做判断。

理由：单镜头重复只能证明自洽。同一个问法带着同一个偏误，问十遍还是同一句话。只有**问法不同**的两个镜头撞到同一件事，才是"这条抱怨不依赖于怎么问"，才值得你花时间去核对原文。

- 「多个镜头都提到」→ 进下表逐条判断。
- 「只有一个镜头反复提到」→ 先放着。它是这个问法自带的视角，不一定是论文的毛病。若你有理由相信它（比如 `reader` 反复说"读者会误解"，而那一节确实绕），再单独核实。
- 「只出现过一次」→ 默认不进判断。除非你自己读原文时也起过疑心——那说明它不是幻觉，只是别的镜头没问到。

这条规则会显著减少你要核对的数量。实测一篇 4 镜头 × 2 次的稿子：一次性的 64 条、单镜头重复 6 条、**跨镜头一致只有 5 条**。判断 5 条比判断 75 条现实得多，而且那 5 条正是最像真人审稿意见的。

### 逐条判断

对进入判断的每一条，标一个处置：

| 处置 | 含义 | 动作 |
| --- | --- | --- |
| **接受** | 现象为真，论文确实有这个毛病 | 改稿；记下改哪一处 |
| **部分接受** | 指出的现象是真的，但给的原因/修法不对 | 改现象，不采纳它给的方案 |
| **误解** | 它读错了（漏看某节、把符号看反、把两种口径混了） | 不改；记下反驳理由和行号 |
| **证据不足** | 它这么问是因为附件里确实没有相关数据 | 要么补数据/补说明，要么写成已知限制 |
| **无关** | 格式、措辞偏好 | 一般忽略 |

**注意：「多个镜头都提到」不等于「成立」。** 镜头之间不是独立的评委——它们共享同一个模型、同一次附件读取、同一份上下文。三个镜头同时漏读同一节，就会同时得出同一个错误结论。跨镜头一致只是把"措辞噪声"和"单问法偏执"滤掉，**它不能替代你回原文核对**。

### 判断的依据只能是论文自己的正文

不是因为它说得"像"有道理。核对要落到**行号**：在 `.tex` 里找到那条数字/那句话，确认现象存不存在。
**现象为真才谈修法；现象为假，就把反驳理由写进台账**，防止下一轮又被问一遍。

### 两个真实例子（它们都"看起来很有道理"，但只有一个成立）

**例 1：成立的 —— 头条数字归属矛盾**

> 它说：`\hat L = -26.3 mH` 被归为 NCL，但 §VII-D 说同一方向是 BLF。

回原文看：`σ₃/σ₁ = 1.9×10⁻³`、`D_L = 0.48 @ N=570` 确实写在 §VII-D 的 BLF 分支下，而 Table II 把同一行同时标了 "NCL, BLF"。
而论文自己定义的五道门里 G3 先于 G4 判定——按自己的分类器，这两类**不可能同时成立**。
→ **接受**。这是内部不自洽，不是读者误读。

**例 2：不成立的 —— "18.2% 说明方法没有普适性"**

> 它说：在公开电池数据集上只复现 18.2%，说明方法不适用。

回原文看：那份数据是 1 Hz 采样，`∂y/∂R₀ = -I_k` 里**没有 `e^{-Δt/τ}` 因子**，机制上结构性不适用——不是"方法失效"，是"这个场景里那个机制根本不存在"。
→ **部分接受**。原文对 18.2% 的叙述确实容易被读成"方法有边界"，但它的因果解释是错的。改叙述，不采纳它的诊断。

**这两种情况长得很像。** 区分它们只能靠回原文，不能靠读起来顺不顺。

## 第三步：改（你执行）

只改「接受」和「部分接受」的条目。每条留痕：

```markdown
| 意见 | 处置 | 证据（行号） | 改动 |
| --- | --- | --- | --- |
| \hat L 归属与 §VII-D 冲突 | 接受 | §VII-D L812 vs Table II L845 | Table II 拆成两行，标明 −26.3 来自 electrical-only 回归器 |
| 18.2% 被当作方法边界 | 部分接受 | §VIII-C L690 | 改写为"该数据集缺少 τ_e 量级，机制不存在"，不采纳其"普适性不足"定性 |
| Fig.3(b) 证书自相矛盾 | 误解 | L723–L728 | 不改；它把 nominal 配置读成了被拒配置 |
```

原则：

1. **先复核现象，再动笔。** 判为"误解"的一个字都不改。
2. **一次只改一处能验证的东西。** 改完能说清"哪一行、为什么"。
3. **不改实验数据。** 涉及"补实验"时，只能在正文里降低主张强度或写明限制，**不能编数据**。
4. **不原地覆盖。** 改前留原版（如 `V3.8`），改后另存新版本目录（如 `V3.9`）。

## 第四步：再发（迭代）

改完再跑一次第一步。**看问题，不看分数。**

维护一张跨轮台账（这是这个包唯一要求你手工做的记录）：

```markdown
| 编号 | 问题 | 首轮出现 | 本轮状态 |
| --- | --- | --- | --- |
| R1 | \hat L 归属矛盾 | 第 1 轮 reject-tie | 已修（第 2 轮未再提，且原文已改） |
| R2 | RC 见证被判为 IDZ 而非 NAT | 第 1 轮 reject-tie | **未修**（第 2 轮未提，但原文没改 —— 它只是没再读到） |
| R3 | N^{-0.558} 无置信区间 | 第 1 轮 reject-tie | 待补 |
```

**为什么必须有这张表：** 第二轮不再提某条，可能是修好了，也可能是它这次没注意到。
没有台账，你分不清这两种情况，就会把"没被提"误当成"已解决"。

判断收敛的标准不是分数稳定，而是：**新跑一轮的产出，没有一条是台账里没出现过的新问题。**

## 已知限制（都是实测出来的）

- **并发上限约 2 路。** 第 3 路服务端静默返回空流（`text="" status=null tokens=0`）。多镜头是**串行**跑的，别改成并发。
- **单次约 10–25 秒**，深度思考 + 联网同开时首个 token 可能 >120s。默认超时 900s。
- **附件必须保留 `file-` 前缀**，去掉 → HTTP 422 空 body。
- **`\input` 不会被展开。** 多文件工程先合并成单文件再发。
- **PoW 依赖站点 wasm**（本包 `wasm/sha3_wasm_bg.wasm`，26612 字节）。站点换实现就要重新取，`pow_selftest` 会暴露。
- **语言会漂移。** 不 pin 语言时，同一问题可能一次英文一次中文，导致无法跨轮比对——所以 `PINS` 里钉了"请用中文回答"。
- **定位符遵从率约 13%。** 即便要求"每条后标注章节或公式号"，也只有约七分之一的句子真标了。别指望它稳定给出可定位的引用。

```
│   ├── findings.mjs         ← 问题聚类（文档频率过滤 + 合取判据）
│   ├── rubric.mjs           ← 8 维度定义（可选多路模式用）
│   ├── personas.mjs         ← 六种审稿角色（可选）
│   └── review.mjs           ← 多路评审编排（可选）
├── tools/
│   ├── ask-paper.mjs        ← **主入口**：发文件 → 问一条或多条 → 可选追问 → 落盘
│   ├── round-report.mjs     ← 把多轮 JSON 汇总成台账（跨镜头一致才算稳定）
│   └── review-paper.mjs     ← 可选：多路 persona 评审
└── test/
    ├── rubric.test.mjs       ← 评分逻辑单测（不联网）
    └── doc.test.mjs          ← 文档与代码一致性检查（不联网）
```

`npm test` 跑全部三个单测，不联网也不需要 token。

`core/` 是自包含的：把整个 `skills/paper-review-deepseek/` 目录拷到任何地方都能直接跑，不需要另外 clone 仓库。
（已实测：复制到临时目录后独立运行，exit=0。）

### 可选：多路评审

想要"多位互不可见的审稿人 + 主编归并"时：

```bash
node tools/review-paper.mjs paper.tex --personas 5 --thinking
```

六种角色（`theory` / `experiment` / `argument` / `journal` / `adversary` / `reproduce`），8 维度打分，中位数聚合。
适合投稿前想知道"会不会被拒"；**不适合日常改稿**——意见互相重复，判断成本比单路高得多，而且如上所述分数本身不稳。
